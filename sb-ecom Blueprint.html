System Architecture

Target design. Today the repo is one Spring Boot 4 app. The service boxes show where modules can split out once their Kafka contracts are stable.

Layers · what each tier does
1 · Edge
Absorbs traffic spikes and bots before they reach the app.
CDN + image transformsWAFBot checks: login, checkoutHTTP/2 + Brotli
2 · Gateway & identity
One place for routing, token checks and rate limits.
Stateless JWT verifyToken-bucket limitsOAuth2 one-time codeRBAC + TOTP (admin, seller)
3 · Modules
Catalog, cart, order, payment, notification, user. Each owns its tables and talks through interfaces or events.
Spring Boot 4.1.2ArchUnit boundary testsMapStruct on hot pathsRFC 9457 Problem Details
4 · Async events
State changes leave through an outbox, so the database and Kafka never disagree.
Kafka 4.x KRaft · RF 3min.insync.replicas = 2Outbox relayIdempotent consumers.DLT topics
5 · Caching
Four tiers, each with its own TTL and invalidation rule.
CDN + ETagCaffeine (in-process)Redis 7Single-flight locks
6 · Search & read models
Shoppers search an index built from events. The primary database serves writes.
Elasticsearch 8+ aliasCo-purchase ZSETsAnalytics to S3 (Parquet)
7 · Data
Primary for writes, replica for listings and reports.
PostgreSQL 16+ primaryRead replicaFlyway migrationsOrders partitioned by monthS3 for images
8 · Real-time
Order status reaches the screen without a refresh. A reconnect fetches the latest state, so no update is lost.
SSE order streamRedis pub/sub fan-outLast state cached per order
9 · Observability
Every request and event carries one trace ID, from browser to consumer.
OpenTelemetryPrometheus + GrafanaJSON logs with traceIdSLO burn alerts
10 · Secrets & flags
No credentials in source. New checkout logic ships dark, then ramps 5 → 50 → 100%.
Vault or K8s secretsOpenFeature flagsCanary ingress rules

Customer Journey & Smooth Transitions

Eight stages from first visit to repeat purchase. Each shows what the shopper sees, how the change should feel, what the system does, and the latency it must meet.

Stages
1
Discover
Sees
Category grid with skeleton tiles sized like the final cards. Images fade in from a blurred preview.
Transition
A tile opens into the product page with a shared-image morph (View Transitions API, with a fade as fallback).
System
Listing served from the CDN (s-maxage=60, stale-while-revalidate=300). Cache misses read the replica.
Emits
product_viewed to analytics-events. LPUSH recent:{userId}.
LCP < 2.5 s · listing p95 < 150 ms on cache hit
2
Search
Sees
Suggestions after two characters. Typos still match. Facets update in place.
Transition
Previous results stay on screen until new ones arrive, so the list never flashes empty. The URL updates, so Back returns to the same results.
System
Edge n-gram index for suggestions, fuzzy match for results. If Elasticsearch times out, fall back to a short replica query.
Emits
search_performed (query, hits). Zero-hit queries feed a merchandising report.
suggest p95 < 80 ms · search p95 < 300 ms
3
Product
Sees
Price, stock state ("Only 3 left" below a threshold), delivery estimate for the shopper's postcode, wishlist heart.
Transition
The heart fills at once. If the request fails, it reverts and a toast says why.
System
Product JSON from Redis (10 min). Stock comes from the inventory cache, never from product JSON.
Emits
product_viewed. wishlist_added writes the wishlists table.
detail p95 < 120 ms on cache hit
4
Cart
Sees
Quantity and header badge update instantly. A guest cart survives a refresh.
Transition
On login the guest cart merges into the account cart. If stock or price changed, one panel explains it before checkout.
System
Cart hash in Redis, written through to cart_items. Merge rule: quantity = min(guest + account, stock). Prices re-read on every view.
Emits
cart_updated, which starts the abandonment clock.
add-to-cart p95 < 200 ms
5
Checkout
Sees
One screen. Saved address and payment method preselected. Tax, coupon and points each on their own line.
Transition
A price or stock change blocks payment with a diff ("1,299.00 is now 1,199.00. Continue?"). It is never a surprise on the last step. Form input survives errors.
System
Checkout saga starts (see Order Engine). Stock held 10 minutes. Coupon applied with a conditional update.
Emits
checkout_started, checkout_step_completed.
checkout API p95 < 1.2 s, excluding gateway
6
Pay
Sees
Gateway sheet opens inline with UPI, cards or wallets. 3-D Secure appears inside the same sheet.
Transition
A "Processing payment" state with a progress line, never a blank screen. If the webhook is slow: "Confirming with your bank", then the order streams in.
System
Payment intent keyed by orderId. Webhook signature checked, de-duplicated on gateway_payment_id, then PAYMENT_SUCCESS written to the outbox.
Emits
payment_success or payment_failed to payment-events.
webhook to PAID p99 < 3 s
7
Track
Sees
Live timeline: Placed, Confirmed, Packed, Shipped, Out for delivery, Delivered. It moves without a refresh.
Transition
Each milestone animates in once. After a dropped connection the page reloads the current state over REST before it reconnects, so nothing is missed.
System
order-events feed Redis pub/sub, which fans out to SSE connections. Last state cached per order for the first paint.
Emits
None new. Reads ORDER_* events.
status event on screen p99 < 2 s
8
Review & return
Sees
"Rate your purchase" three days after delivery, with items prefilled. Points-earned toast. One-tap reorder.
Transition
The prompt is a dismissable card. It never blocks the page and is never shown twice.
System
Scheduled job after ORDER_DELIVERED. reviews.is_verified set from order_items. loyalty_ledger earn entry.
Emits
review_requested to notification-events. points_earned.
review prompt 72 h ± 1 h after delivery
Transition rules
Optimistic, then reconcileCart, quantity and wishlist changes show at once. The server reply confirms them or rolls them back with a reason.
Never blankSkeletons match the final layout. Keep the last results on screen while the next request runs.
Stable layoutReserve image and price boxes with aspect-ratio. Target CLS under 0.1.
Price truth at checkoutThe order stores the price the shopper accepted. Any change before payment needs an explicit confirm step.
Recoverable errorsA failed payment keeps the cart, address and form values. Retries reuse the same Idempotency-Key, so a double tap never charges twice.
Motion with restraint150 to 280 ms ease-out for panels and toasts. Everything respects prefers-reduced-motion.
Live without refreshOrder status streams over SSE. If the stream drops, fall back to polling every 30 s.
Guest to memberA guest keeps the cart, wishlist and recently viewed list after signing up. Nothing is lost at the moment of conversion.

Order Engine & Checkout Saga

One state machine decides every order transition. A saga with compensations keeps stock, coupons and payment consistent. A transactional outbox keeps the database and Kafka in step.

Order state machine
Allowed transitions
From → ToTriggerGuardEmits
PENDING_PAYMENT → PAIDpayment.captured webhookSignature valid; amount equals order totalPAYMENT_SUCCESS
PENDING_PAYMENT → PAYMENT_FAILEDGateway failure, or 30 min with no captureNo captured payment existsPAYMENT_FAILED; holds released
PAID → CONFIRMEDOrder consumer on PAYMENT_SUCCESSHolds committed to on_handORDER_CONFIRMED
PAID or CONFIRMED → CANCELLEDCustomer or adminBefore PACKEDORDER_CANCELLED; refund if paid
CONFIRMED → PACKEDWarehouse scanEvery line scannedORDER_PACKED
PACKED → SHIPPEDCarrier pickup webhookTracking number presentORDER_SHIPPED
SHIPPED → OUT_FOR_DELIVERYCarrier scanNoneORDER_OUT_FOR_DELIVERY
OUT_FOR_DELIVERY → DELIVEREDProof of deliveryNoneORDER_DELIVERED; starts review and points
DELIVERED → RETURN_REQUESTEDCustomerWithin 7 days of deliveryRETURN_REQUESTED
RETURN_REQUESTED → RETURNEDItem received at warehouseItem matches an order lineRETURN_RECEIVED
CANCELLED or RETURNED → REFUNDEDGateway confirms refundRefund ≤ captured amountREFUND_COMPLETED

All transitions go through one OrderStateMachine class. Controllers and consumers request a transition and never set status directly. Illegal moves throw. Every accepted move writes order_status_history and an outbox row in the same transaction.

Checkout saga, with compensations
#StepIf a later step fails, compensate with
1Re-price the cart from the database and compare with what the shopper saw.Nothing to undo. Return 409 with the price diff.
2Create the order as PENDING_PAYMENT, with ORDER_PLACED in the outbox.Mark CANCELLED.
3Hold stock in inventory_reservations for 10 minutes.Release the hold (reserved minus quantity).
4Apply the coupon: UPDATE coupons SET used_count = used_count + 1 WHERE used_count < max_uses.Decrement used_count.
5Create the gateway payment intent, keyed by orderId.Cancel the intent at the gateway.
6Shopper pays. A verified, de-duplicated webhook moves the order to PAID.If the order was already cancelled, refund automatically.
7Commit holds to on_hand, clear the cart, emit ORDER_CONFIRMED.Nothing. Every step is idempotent, so a retry is safe.
Reconciliation job, every 5 minutesOrders still PENDING_PAYMENT after 15 minutes get a status check at the gateway. A capture the gateway holds but we missed is written in. Orders with no capture after 30 minutes become PAYMENT_FAILED.
Messaging guarantees
Transactional outboxThe order row and its outbox_events row commit together. A relay (Debezium CDC, or a poller using FOR UPDATE SKIP LOCKED) publishes to Kafka with key = orderId. No dual writes.
Idempotent producersenable.idempotence=true, acks=all, replication factor 3, min.insync.replicas=2. Losing one broker never loses an acknowledged event.
Idempotent consumersprocessed_events(consumer_group, event_id) is checked in the same transaction as the side effect. Duplicates are skipped.
Ordering by keyorder-events are keyed by orderId and stock events by productId, so each entity's events stay in order. Order across entities is not promised.
Retry, then DLTThree attempts with backoff (1 s, 4 s, 16 s, plus jitter), then the record goes to <topic>.DLT. Alert when DLT depth is above zero. Replay after the fix.
Idempotency-Key on writesPOST /api/v1/orders and POST /api/v1/payments. Same key and body return the stored response. Same key with a different body returns 422.

Hot keys and stampedesA product that goes viral can expire under load. A single-flight lock (SET NX PX 3000) lets one request rebuild the value while others wait up to 100 ms or serve the stale copy. Refresh early at 80% of TTL so keys never expire in unison.
Search as a read model
Index and aliasproducts_v{n} in Elasticsearch, read through a products alias. Built from product-events, keyed by productId.
Zero-downtime reindexBuild products_v{n+1} in the background, replay the topic, then move the alias. Drop the old index a day later.
AnalyzersEdge n-gram for suggestions, standard analyzer for results, synonyms (tv = television), fuzziness AUTO for typos.
Facets from the same queryCategory, brand, price range, rating and in-stock counts come from the search that produced the results, so they never disagree.
RankingRelevance first, then 30-day sales, then in-stock. Out-of-stock items sink to the end; they are never removed.
DegradationIf Elasticsearch is down, search falls back to a 20-item replica query on name and slug, with a notice that results may be limited.

Refresh tokensStored as SHA-256 hashes and rotated on every use. A reused token revokes the whole family.
OAuth2One-time code, valid 60 s, exchanged by POST. Tokens never appear in a URL, browser history or a log.

PaymentsThe gateway holds tokenised card data. The store keeps no card numbers, which keeps PCI scope small.
